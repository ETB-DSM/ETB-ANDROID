# 경로 파싱 수정 — TMAP LineString 경로점 반영

작성일: 2026.08.26

## 배경 / 문제

TMAP 보행자 경로 API(`POST /tmap/routes/pedestrian`)는 정상적으로 `200`을 반환하지만,
앱 내에서 그 데이터를 소비하는 과정에 구조적 버그가 있어 **경로 재탐색(REROUTE)이 무한 반복**된다.

### 근본 원인

TMAP 응답의 `features`는 두 종류로 구성된다.

| geometry.type | 의미 | coordinates 구조 |
|---|---|---|
| `Point` | 회전/안내 지점 (드문드문) | `[lng, lat]` |
| `LineString` | 실제 걷는 경로선 (촘촘한 좌표열) | `[[lng,lat], [lng,lat], ...]` |

현재 `NavigationRepositoryImpl.fetchRoute`는 `filter { it.geometry.type == "Point" }`로
**`LineString`(실제 경로선)을 전부 버리고 회전 지점만** `config.steps`에 담는다.

그 결과 `ActionCalculator.calculate`의 이탈 판정:

```kotlin
val minDistToRoute = steps.minOf { haversine(lat, lng, it.latitude, it.longitude) }
if (minDistToRoute > 30.0) return NavigationAction.REROUTE to 0.0
```

에서 `steps`가 드문 회전 지점뿐이라, 사용자가 두 회전 지점 사이 직선 구간만 걸어도
가장 가까운 점이 30m를 넘어 **경로 이탈로 오판 → REROUTE**. 재탐색해도 동일한 드문 경로를 받아
**무한 반복**된다. 화면에는 정상 안내 대신 "경로 재탐색"만 계속 표시된다.

## 목표

`LineString`의 촘촘한 경로 좌표를 이탈 판정용 경로점으로 살리고,
`Point`의 회전 정보는 회전 노드로 유지하여 이탈 판정과 회전 안내가 모두 정상 동작하게 한다.

## 상세 설계

### `fetchRoute` 파싱 재작성

feature를 **순서대로** 순회하며 type에 따라 분기해 `RouteStep`으로 펼친다.

```kotlin
override suspend fun fetchRoute(
    startLat: Double, startLng: Double,
    endLat: Double, endLng: Double,
): Result<List<RouteStep>> = runCatching {
    val response = tmapPedestrianApi.getPedestrianRoute(
        request = TmapPedestrianRequest(
            startX    = startLng, startY = startLat,
            endX      = endLng,   endY   = endLat,
            startName = java.net.URLEncoder.encode("출발지", "UTF-8"),
            endName   = java.net.URLEncoder.encode("목적지", "UTF-8"),
        )
    )
    response.features.flatMap { feature ->
        when (feature.geometry.type) {
            "Point" -> {
                val coords = feature.geometry.coordinates.jsonArray
                val lng = coords[0].jsonPrimitive.double
                val lat = coords[1].jsonPrimitive.double
                val turnType = when (feature.properties.turnType) {
                    12, 16, 18, 212 -> TurnType.LEFT
                    13, 17, 19, 213 -> TurnType.RIGHT
                    else            -> TurnType.STRAIGHT
                }
                listOf(
                    RouteStep(lat, lng, feature.properties.distance, turnType, feature.properties.description)
                )
            }
            "LineString" -> {
                feature.geometry.coordinates.jsonArray.map { pair ->
                    val p   = pair.jsonArray
                    val lng = p[0].jsonPrimitive.double
                    val lat = p[1].jsonPrimitive.double
                    RouteStep(lat, lng, feature.properties.distance, TurnType.STRAIGHT, feature.properties.description)
                }
            }
            else -> emptyList()
        }
    }
}
```

### 동작 근거

- **이탈 판정 정상화**: `LineString`에서 나온 촘촘한 경로점 덕분에 `minDistToRoute`가
  실제 경로 위에서 항상 작게 유지되어 오판 REROUTE가 사라진다.
- **회전 안내 유지**: `Point` 회전 노드는 실제 `turnType`을 담고, `LineString` 점은
  `STRAIGHT`이므로 `ActionCalculator`의 `firstOrNull { it.turnType != STRAIGHT }`가
  다음 회전 노드를 정확히 찾는다.
- **순서 보존**: `flatMap`이 feature 순서를 유지하므로 경로 진행 방향이 보존된다.
- `RouteStep.distanceMeters`는 `ActionCalculator` 로직에서 사용되지 않으므로(좌표·turnType만 사용)
  `LineString` 점에 링크 거리를 넣어도 안내 로직에 영향 없다.

## 테스트 방법
1. 앱에서 목적지 설정 후 길안내를 시작한다.
2. 경로 위를 정상적으로 이동할 때 화면이 "경로 재탐색"에 갇히지 않고
   직진/좌회전/우회전 안내가 표시되는지 확인한다.
3. OkHttp 로그에서 `POST .../instructions` 의 `action`이 `reroute`로 도배되지 않고
   실제 경로 이탈 시에만 나타나는지 확인한다.
4. 실제로 경로를 30m 이상 벗어났을 때만 REROUTE가 발생하는지 확인한다.
