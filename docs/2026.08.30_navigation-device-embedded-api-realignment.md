# Navigation / Device Status — Embedded API 정합화

## 배경

ETB-BE 서버 로그 분석 결과로 3가지 404 패턴이 보고되었다(`devices/status` 오타, `nav_001` 하드코딩, `/api/v1/api/...` prefix 중복). 이 저장소(ETB-ANDROID)에서 해당 문자열을 전수 조사했으나 전혀 존재하지 않았고, 보고된 3가지 요청은 전부 **Embedded API**(`/api/...`, Orange Pi 전용, userId 기반, JWT 불필요) 형태였다. 이 저장소에는 Orange Pi 클라이언트 코드가 없으므로 최초 보고 내용 자체는 이 저장소와 무관하다고 판단했다.

그런데 Notion(`ETB > Embedded와 통신 API > API 명세서`)을 확인한 결과, 사용자가 "설계중 라벨은 오표시이고 실제로는 서버에 이미 다 구현되어 있다"고 확인해주었다. 이 스펙을 현재 앱 코드와 대조한 결과, **정말로 앱이 잘못된 엔드포인트/요청·응답 형식을 쓰고 있는 지점 2곳**을 발견했다. 원래 보고된 3가지 버그와는 별개의, 이 저장소 안에서 고쳐야 할 실제 문제다.

## 확인된 불일치

### 1. 디바이스 상태 조회 (`DeviceApi.getDeviceStatus`)

- 파일: `app/src/main/java/com/aicane/app/data/remote/api/DeviceApi.kt:20`
- 현재: `GET api/v1/devices/{deviceId}/status`
- Notion 스펙("device status check", 사용 위치: "앱 또는 보호자 화면에서 장치 상태 확인"): `GET /api/devices/{deviceId}/status` — **`v1` 없음**
- 응답도 형태가 다르다.
  - 현재 `DeviceStatusResponse`(`app/src/main/java/com/aicane/app/data/remote/dto/device/DeviceStatusResponse.kt`): 최상위에 `deviceId, battery, lidarOk: Boolean, cameraOk: Boolean, gpsOk: Boolean, networkOk: Boolean, createdAt` — 래퍼 없음, boolean 필드.
  - Notion 실제 응답: `{"status":"OK","message":"...","data":{"userId":...,"deviceId":...,"battery":72,"lidarStatus":"ok","cameraStatus":"ok","gpsStatus":"ok","networkStatus":"ok","timestamp":"..."}}` — **`data`로 래핑, 상태값은 boolean이 아니라 `"ok"/"error"` 문자열, `createdAt`이 아니라 `timestamp`.**
  - 현재 DTO로는 `data` 안의 값을 읽지 못하고 최상위 필수 필드(`deviceId`, `battery` 등)가 없어 역직렬화 시 실패한다. 경로만 고쳐서는 정상 동작하지 않는다.
- 영향: `NavigationViewModel`(`presentation/navigation/NavigationViewModel.kt:111`)이 길안내 중 지팡이 배터리/연결 상태를 표시하는 데 이 API를 쓴다 (가장 최근 커밋 `dded71c`). 즉 **가장 최근에 추가된 "길안내 중 지팡이 상태 표시" 기능이 현재 서버에서 정상 동작하지 않을 가능성이 높다.**

### 2. 길안내 세션 API (`NavigationApi`)

- 파일: `app/src/main/java/com/aicane/app/data/remote/api/NavigationApi.kt`
- 현재 3개 메서드 모두 `api/v1/navigation/sessions...` (App API, JWT) 형태로 구현되어 있고, 이는 저장소 안의 `api.md`(App API 섹션)와는 일치한다.
- 그러나 Notion 스펙에서는 세션 생성/명령 전송/상태 변경이 **App API가 아니라 Embedded API(`/api/navigation/sessions...`, `v1` 없음, JWT 대신 userId/deviceId 바디 전달)로 신규 추가(`구분: 추가`)** 되어 있고, 사용 주체도 "앱"으로 명시되어 있다.
  - `POST /api/v1/navigation/sessions` (App API, 현재 구현) → 실제로는 `POST /api/navigation/sessions` (Embedded API)
    - 현재 요청 `CreateSessionRequest(destinationId)` → 실제 요구: `userId, deviceId, destinationId, startLatitude, startLongitude, timestamp`
    - 현재 응답 `CreateSessionResponse(sessionId)` (평문) → 실제 응답: `{"status":"CREATED","message":"...","data":{"navigationSessionId":"..."}}`
  - `POST /api/v1/navigation/sessions/{id}/instructions` → 실제: `POST /api/navigation/sessions/{id}/instruction` (**단수형**, path variable 이름도 `navigationSessionId`)
    - 현재 요청 `CreateInstructionRequest(action, distanceMeters, message)` → 실제 요구: `action, distanceMeters, message, latitude, longitude, timestamp` (위치·시간 필드 추가 필요)
  - `PATCH /api/v1/navigation/sessions/{id}/status` → 실제: `PATCH /api/navigation/sessions/{id}/status` (`v1` 없음)
    - 현재 요청 `UpdateStatusRequest(status)` → 실제 요구: `status, reason, timestamp` (`reason`, `timestamp` 추가 필요)
- `NavigationRepositoryImpl`이 이 3개 메서드를 그대로 감싸서 `DestinationListViewModel.startNavigation()`(세션 생성), `NavigationService`/`NavigationViewModel`(명령·상태 전송)에서 쓰고 있다. 원래 로그 분석에서 "`POST /api/v1/navigation/sessions` 호출 기록이 한 번도 없다"고 한 것도, 애초에 서버가 이 경로(App API v1)를 구현하지 않았고 Embedded 경로만 구현되어 있었기 때문일 가능성이 크다.

## 미해결 질문 (진행 전 확인 필요)

1. **인증 방식**: Embedded API는 JWT 없이 userId 기반이다. 현재 `NavigationApi`/`DeviceApi.getDeviceStatus`는 `@AppClient` Retrofit(= `AuthInterceptor`가 JWT를 자동 첨부, `TokenAuthenticator`가 401 시 refresh 시도)을 그대로 쓰고 있다.
   - (a) 그대로 두고 경로/DTO만 고친다 (JWT는 그냥 얹혀 보내지되 서버가 무시한다고 가정) — 변경 범위 최소.
   - (b) 이 엔드포인트들만 JWT를 첨부하지 않는 별도 Retrofit 인스턴스로 분리한다 — Embedded API 의도에 더 부합하지만 변경 범위 커짐.
2. **userId 획득**: `TokenStorage.userId`가 로그인 응답(`LoginResponse.userId`)으로 이미 저장되고 있어 재사용 가능해 보이는데, 맞는지 확인 부탁한다.
3. **deviceId 획득**: `GetPairedDeviceIdUseCase` → `TokenStorage.deviceId`(디바이스 등록 시 저장)를 그대로 세션 생성 요청에 실어 보내면 될지 확인 부탁한다. 디바이스가 등록되어 있지 않은 사용자가 길안내를 시작하면 어떻게 처리할지도 정책이 필요하다(현재는 디바이스 없어도 길안내 자체는 가능한 구조).
4. **응답 래퍼 처리 범위**: `data` 래퍼 + `status`/`message` 형식이 Embedded API 전반의 공통 포맷으로 보인다. 이번 건(디바이스 상태, 내비게이션 3종)에 한해 DTO를 개별로 고칠지, 아니면 공통 래퍼 타입(`EmbeddedResponse<T>` 같은)을 만들어 재사용할지 방향을 정해야 한다.
5. **`api.md` 갱신**: CLAUDE.md 규칙상 API 변경 시 `api.md`를 갱신해야 한다. 이번 건은 앱 코드가 기존에 잘못 따르고 있던 `api.md`(App API 섹션의 navigation/device-status 관련 서술)를 실제 스펙에 맞게 고쳐야 하는데, `api.md`가 Notion과 별개로 관리되는 문서인지, Notion을 최신 소스로 보고 `api.md`도 동기화해야 하는지 확인 부탁한다.

## 결정 사항 (사용자 피드백 반영)

1. **인증 방식 → (b) 채택**: `DeviceApi.getDeviceStatus`·`NavigationApi`의 3개 메서드를 JWT를 첨부하지 않는 별도 Retrofit 클라이언트(`@EmbeddedClient`)로 옮긴다.
2. **deviceId 없으면 길찾기 차단**: `NavigationRepositoryImpl.createSession`에서 `TokenStorage.deviceId`가 없으면 네트워크 호출 전에 즉시 실패(`Result.failure`)시켜 길안내 시작을 막는다. 기존 `DestinationListViewModel.startNavigation`의 실패 처리 경로(`errorMessage` 표시)를 그대로 재사용한다.
3. **userId**: `TokenStorage.userId`(로그인 응답에서 저장됨)를 그대로 사용.
4. **응답 래퍼**: 공통 제네릭 `EmbeddedEnvelope<T>(status, message, data)`를 도입해 재사용.
5. **api.md 동기화**: Notion에서 확인된 실제 스펙(디바이스 상태 조회/업데이트 경로 복수형, 길안내 세션 3종 API가 App API v1이 아닌 Embedded API 소속)을 반영해 `api.md`를 갱신.

## 실제 구현 내용

- `di/qualifier/EmbeddedClient.kt` — 신규 Qualifier
- `di/NetworkModule.kt` — `@EmbeddedClient` OkHttpClient/Retrofit 추가 (AuthInterceptor/TokenAuthenticator 미부착)
- `di/EmbeddedModule.kt` — `EmbeddedApi` 프로바이더 신규
- `di/NavigationModule.kt` — `provideNavigationApi` 제거 (더 이상 App API 사용 안 함)
- `data/remote/api/EmbeddedApi.kt` — 신규: `getDeviceStatus`, `createSession`, `createInstruction`, `updateSessionStatus`
- `data/remote/api/NavigationApi.kt` — 삭제
- `data/remote/api/DeviceApi.kt` — `getDeviceStatus` 제거 (App API v1에는 없는 엔드포인트였음)
- `data/remote/dto/embedded/*` — 신규 DTO 6종 (`EmbeddedEnvelope`, `EmbeddedDeviceStatusData`, `CreateNavigationSessionRequest/Data`, `CreateNavigationInstructionRequest`, `UpdateNavigationSessionStatusRequest`)
- `data/remote/dto/navigation/*`, `data/remote/dto/device/DeviceStatusResponse.kt` — 삭제 (Embedded DTO로 대체)
- `data/repository/DeviceRepositoryImpl.kt` — `EmbeddedApi` 주입, `getDeviceStatus` 응답 언래핑 로직
- `data/repository/NavigationRepositoryImpl.kt` — `EmbeddedApi` + `TokenStorage` 주입, deviceId/userId 검증, 3개 메서드 요청/응답 형식 전면 수정
- `domain/repository/NavigationRepository.kt`, `domain/usecase/navigation/{CreateSessionUseCase,CreateInstructionUseCase,UpdateSessionStatusUseCase}.kt` — 시그니처 변경(위치 좌표, reason 추가)
- `domain/model/NavigationInstruction.kt` — `latitude`/`longitude` 필드 추가
- `service/NavigationService.kt`, `navigation/ActionUploader.kt` — 명령 업로드 시 현재 위치 전달
- `presentation/destination/DestinationListViewModel.kt` — 길안내 시작 시 현재 위치 조회 후 세션 생성 요청에 포함
- `api.md` — 위 결정사항 5 반영
