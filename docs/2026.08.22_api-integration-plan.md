# API 연동 전체 작업 계획

## 개요

현재 프레젠테이션 레이어만 구현된 상태에서,
주소 검색 Open API 선택 → UI 불일치 수정 → 전 레이어 API 연동까지의 전체 작업 계획을 정의한다.

---

## 1. 주소 검색 Open API 선택

### 후보 비교

| 항목 | T-Map POI 검색 | Kakao Local API |
|------|---------------|----------------|
| API 키 | TMAP_API_KEY (이미 사용 중) | 별도 Kakao REST API Key 필요 |
| 요청 방식 | `GET /tmap/pois?searchKeyword=` + `appKey` 헤더 | `GET /v2/local/search/keyword.json` + `Authorization: KakaoAK` 헤더 |
| 좌표 필드 | `noorLat`, `noorLon` (String) | `y` (lat), `x` (lng) (String) |
| 장소명 | `name` | `place_name` |
| 주소 | `upperAddrName + middleAddrName + roadName` 조합 | `road_address_name` 또는 `address_name` |
| 한국 데이터 품질 | 우수 | 우수 |
| 무료 한도 | 일 10만 건 | 일 30만 건 |

### 선택: **T-Map POI 검색**

**이유:**
- `TMAP_API_KEY` 하나로 경로 API와 POI 검색을 모두 처리 → 키 관리 부담 없음
- 이미 T-Map OkHttp 클라이언트를 구성해야 하므로 추가 비용 없음
- 경로 API와 동일한 좌표계(WGS84GEO) 사용 → 변환 불필요

### T-Map POI API 명세

```
GET https://apis.openapi.sk.com/tmap/pois
Header: appKey: {TMAP_API_KEY}
Params:
  searchKeyword: String       # 검색어
  count: Int = 10             # 결과 수
  resCoordType: "WGS84GEO"

Response:
{
  "searchPoiInfo": {
    "pois": {
      "poi": [
        {
          "name": "강남역",
          "upperAddrName": "서울특별시",
          "middleAddrName": "강남구",
          "roadName": "강남대로",
          "buildingNo1": "396",
          "noorLat": "37.498095",
          "noorLon": "127.027610"
        }
      ]
    }
  }
}
```

### BuildConfig 추가

```kotlin
// app/build.gradle.kts defaultConfig에 추가
buildConfigField("String", "TMAP_API_KEY", "\"${localProperties["TMAP_API_KEY"]}\"")
```

## 2. UI 불일치 수정 범위

현재 코드에서 발견된 UI 불일치를 먼저 수정한다. API 연동 전에 UI가 올바른 데이터 구조를 받을 준비가 되어야 한다.

### 2-1. SearchScreen

**현재 문제:**
- `PlaceResult(name, address)`에 좌표 없음
- 더미 결과 반환 (하드코딩)
- `NavGraph`에서 `onPlaceSelected` 콜백이 선택한 장소를 `DestinationRegScreen`으로 전달하지 않음

**수정 내용:**
```kotlin
// 변경 전
data class PlaceResult(val name: String, val address: String)

// 변경 후 (domain 레이어 준비 전까지 presentation 모델로 유지)
data class PlaceResult(
    val name: String,
    val address: String,
    val latitude: Double,
    val longitude: Double,
)
```
- `results`는 빈 리스트로 변경 (API 연동 후 채울 것)
- 검색어 입력 시 결과 없음 상태 UI 표시

### 2-2. DestinationRegScreen

**현재 문제:**
- PRD 요구 필드: `name`, `targetText`, `latitude`, `longitude`, `radius`
- 현재 필드: `name`, `address` (2개뿐)
- `prefilledAddress`만 받고 좌표를 받지 않음

**수정 내용:**
```kotlin
// 변경 후
@Composable
fun DestinationRegScreen(
    onBack: () -> Unit,
    onSaved: () -> Unit,
    prefilledName: String = "",
    prefilledAddress: String = "",
    prefilledLat: Double = 0.0,
    prefilledLng: Double = 0.0,
)
```
- `targetText` 입력 필드 추가 (라벨: "건물 입구 안내 문자")
- `radius` 입력 필드 추가 (라벨: "도착 반경(m)", 기본값: "30")
- `latitude`, `longitude`는 SearchScreen에서 전달받아 읽기 전용으로 표시
- `address`는 표시만 하고 편집 불가 (SearchScreen에서 확정된 값)

### 2-3. NavGraph — SearchScreen → DestinationReg 데이터 전달

**현재 문제:**
```kotlin
// 현재: 선택한 장소 정보를 DestinationRegScreen으로 넘기지 않음
onPlaceSelected = { navController.navigate(Screen.DestinationReg.route) }
```

**수정 방향:**  
`DestinationReg` route에 파라미터 추가 (`name`, `address`, `lat`, `lng`)

```kotlin
// Screen.kt
data object DestinationReg : Screen("destination_reg?name={name}&address={address}&lat={lat}&lng={lng}") {
    fun createRoute(name: String, address: String, lat: Double, lng: Double) =
        "destination_reg?name=${Uri.encode(name)}&address=${Uri.encode(address)}&lat=$lat&lng=$lng"
}

// NavGraph.kt
composable(
    route = Screen.DestinationReg.route,
    arguments = listOf(
        navArgument("name")    { type = NavType.StringType; defaultValue = "" },
        navArgument("address") { type = NavType.StringType; defaultValue = "" },
        navArgument("lat")     { type = NavType.FloatType;  defaultValue = 0f },
        navArgument("lng")     { type = NavType.FloatType;  defaultValue = 0f },
    )
) { backStackEntry ->
    DestinationRegScreen(
        onBack = { navController.popBackStack() },
        onSaved = { navController.navigate(Screen.DestinationList.route) { popUpTo(Screen.Search.route) { inclusive = true } } },
        prefilledName    = backStackEntry.arguments?.getString("name").orEmpty(),
        prefilledAddress = backStackEntry.arguments?.getString("address").orEmpty(),
        prefilledLat     = backStackEntry.arguments?.getFloat("lat")?.toDouble() ?: 0.0,
        prefilledLng     = backStackEntry.arguments?.getFloat("lng")?.toDouble() ?: 0.0,
    )
}

// SearchScreen onPlaceSelected 콜백
onPlaceSelected = { place ->
    navController.navigate(
        Screen.DestinationReg.createRoute(place.name, place.address, place.latitude, place.longitude)
    )
}
```

### 2-4. SplashScreen — hasSession 항상 false 고정 문제

**현재 문제:**
```kotlin
// NavGraph.kt: hasSession이 항상 false
SplashScreen(
    onNavigateToLogin = { ... },
    onNavigateToList  = { ... },
)
```
SplashScreen이 `hasSession: Boolean = false`를 받지만 NavGraph에서 값을 넘기지 않아 항상 로그인 화면으로 이동.

**수정 방향 (UI 단계):**  
`hasSession` 파라미터를 NavGraph에서 외부 주입받도록 구조 변경.  
실제 토큰 체크는 Phase 3 인증 ViewModel 연동 시 구현한다.  
지금은 NavGraph에서 `hasSession = false`를 명시적으로 전달하는 것으로 통일한다.

```kotlin
SplashScreen(
    onNavigateToLogin = { ... },
    onNavigateToList  = { ... },
    hasSession = false,   // Phase 3에서 ViewModel로 교체
)
```

## 4. 브랜치 전략 요약

```
develop
  └─ fix/ui-destination-search      ← Phase 1 (지금 시작)
  └─ chore/network-infra             ← Phase 2
  └─ feat/auth-api                   ← Phase 3
  └─ feat/device-api                 ← Phase 4
  └─ feat/guardian-api               ← Phase 5
  └─ feat/destination-api            ← Phase 6
  └─ feat/navigation-api             ← Phase 7
  └─ feat/mypage-complete            ← Phase 8
```

Phase 4, 5는 독립적이므로 병렬 작업 가능.  
Phase 6은 Phase 2(인프라) 완료 후 진행.  
Phase 7은 Phase 6 완료 후 진행 (세션 생성이 목적지 선택과 연계).  
Phase 8은 모든 Phase 완료 후.
