## 0. 결론 요약

**디자인 토큰(DESIGN.md ↔ 코드)은 이미 완전히 정합되어 있다.** `2026-08-25` `feat/ui-design-sync` 브랜치(`docs/2026.08.25_ui-design-sync.md`)에서 프로토타입을 기준으로 11개 화면 + 컴포넌트를 이미 맞춰놓았고, `Color.kt` / `Shape.kt` / `Type.kt`는 `DESIGN.md`의 컬러·라운드·타이포 토큰과 1:1로 일치한다. **따라서 "design.md에 맞추는 작업"은 재작업이 필요 없다.**

남은 것은 두 가지뿐이다:
1. **UI/UX 세부 불일치** — 디자인 싱크 이후에도 프로토타입과 다르게 남아있는 인터랙션/레이아웃 6건
2. **기능 격차** — SCREENS.md/PRD 대비 구현되지 않았거나 다르게 동작하는 부분 5건 (그중 1건은 버그성)

## 2. UI/UX 세부 불일치 (디자인 싱크 이후에도 남은 차이)

### 2-1. 목적지 목록 — 스와이프 삭제 없음
- 프로토타입(07번 화면): "왼쪽으로 밀어 삭제 · 카드를 눌러 길안내 시작" — 스와이프 제스처로만 삭제 노출.
- 현재 코드(`DestinationListScreen.kt:174-188`): 카드마다 휴지통 아이콘 버튼이 항상 노출, 탭하면 확인 다이얼로그. 힌트 텍스트도 "카드를 눌러 길안내를 시작하세요"로 스와이프 언급이 빠짐.
- **판단**: 시각장애인 사용자에게는 스와이프보다 상시 노출된 버튼 + 확인 다이얼로그가 오히려 더 접근성이 좋다. **의도적 개선으로 보이며 되돌릴 필요 없음.** 다만 "디자인 프로토타입과 다르다"는 사실 자체는 기록해둔다.

### 2-2. 이메일 인증 — 코드 재전송 액션 없음
- 프로토타입(03번): "코드 재전송" 링크가 OTP 박스 아래 존재.
- 현재 코드(`VerifyScreen.kt`): OTP 6박스 + "확인" 버튼만 있고 재전송 액션이 없다. 코드가 만료되거나 스팸함에 들어가면 사용자가 회원가입을 처음부터 다시 해야 한다.
- **판단**: 이건 UX 결함에 가깝다. `VerifyViewModel`에 재전송 유스케이스가 없으면 API 연동(`POST /auth/verify-email` 재전송 엔드포인트 존재 여부 확인 필요)부터 확인 필요.

### 2-3. 목적지 확인 — 도착 반경이 프리셋 칩이 아니라 자유 입력
- 프로토타입(09번): "도착 인식 반경" 10m/30m/50m 세그먼트 버튼(택1).
- 현재 코드(`DestinationRegScreen.kt:143-150`): `AiCaneTextField` 숫자 자유 입력, placeholder "30".
- **판단**: 자유 입력이 더 유연하지만, "카메라 인식 반경"이라는 도메인 특성상 프리셋이 오히려 오조작을 줄인다. UX 관점에서는 프로토타입 방식(프리셋 칩) 채택을 권장.

### 2-4. 목적지 검색 — 빈 상태 콘텐츠 없음
- 프로토타입(08번): 검색어가 없을 때도 "현재 위치를 목적지로" 라디오 필과 "내 주변 추천 장소" 리스트(카테고리 아이콘 + 거리)를 보여준다.
- 현재 코드(`SearchScreen.kt:122-135`): 검색어가 없으면 "장소명이나 주소를 입력하세요" 안내 텍스트만 중앙에 표시. 현재 위치 목적지 지정 옵션도, 추천 장소 리스트도 없다.
- **판단**: 기능 격차이기도 함 → 3장 참고.

### 2-5. 회원가입 화면 — SCREENS.md 스펙과 실제 구현이 다름 (문서 드리프트)
- `SCREENS.md` 2번 화면은 이메일/비밀번호/비밀번호 확인/이름을 **한 화면**에 모은 단일 폼으로 기술.
- 실제 구현(`SignupScreen.kt`)은 **3단계 위저드**(이메일 → 이름 → 비밀번호, `StepIndicator` "N/3 단계")로, 이는 프로토타입(02번 화면의 "1/3 단계" 진행바)과 일치한다.
- **판단**: 코드가 아니라 `SCREENS.md` 쪽이 오래된 문서다. 코드는 맞고 스펙 문서를 갱신해야 함.

### 2-6. 길안내 종료 화면 — 도착/취소 구분 없음 (2-6은 기능 버그이기도 함, 3-5 참고)

## 3. 기능 격차 (SCREENS.md/PRD 대비)

### 3-1. [버그] 길안내 종료 화면이 "도착"과 "취소"를 구분하지 않는다
- `SCREENS.md` 12번: 도착 시 "도착했습니다!", 취소/오류 시 "길안내를 종료했습니다"로 분기.
- 현재 `NavigationEndScreen.kt`는 `destination`/`walkingTime`/`walkingDistance` 파라미터를 받지만 **NavGraph에서 아무 값도 전달하지 않고**(`NavGraph.kt:258-262`, `onHome`만 전달), 화면 내부에서도 `walkingTime`/`walkingDistance`는 선언만 되고 렌더링에 쓰이지 않는 죽은 파라미터다. 결과적으로 사용자가 "안내 종료"(취소)를 눌러도, 실제 도착해도 항상 동일하게 "도착했어요! / 목적지"만 뜬다.
- **영향**: 시각장애인 사용자가 도중에 안내를 취소했는데 "도착했어요"라는 잘못된 피드백을 받게 됨 — 접근성 맥락에서 특히 심각.
- **권장**: `NavigationViewModel`이 세션 종료 사유(`arrived`/`canceled`/`error`, PRD APP-007)를 이벤트에 실어 NavGraph → NavigationEndScreen까지 전달하고, 화면에서 사유별 문구 분기.

### 3-2. 목적지 검색 — "현재 위치를 목적지로" / "내 주변 추천 장소" 미구현
- 프로토타입에는 있으나 PRD 기능 요구사항(APP-002)에도 명시돼 있지 않다. 신규 요구사항으로 볼지, 스코프 아웃으로 볼지 사용자 결정이 필요.

### 3-3. 이메일 인증 코드 재전송 미구현
- 2-2와 동일 건. `AuthApi.kt`에 재전송 엔드포인트가 있는지부터 확인 필요 (`api.md` 참고).

### 3-4. 마이페이지 — 기기/보호자 다중 등록 불가
- 프로토타입(12번)은 "등록된 지팡이" 섹션에 "+ 추가" 버튼과 기기별 리스트(복수 가능 구조)를 보여준다.
- 현재 구현은 `uiState.deviceId` / `uiState.guardianId` 단일 값 구조(`MypageScreen.kt`, `MypageViewModel`)이며, 추가 등록 진입점(+버튼)이 없다. `DeviceApi`/`GuardianApi`도 목록 조회는 있지만 화면에서 다건을 다루지 않는다.
- **판단**: PRD/API 설계상 다중 기기 지원이 실제 목표인지 먼저 확인 필요 — 목표라면 UI뿐 아니라 상태 모델(`MypageUiState`)부터 리스트로 바꿔야 하는 더 큰 작업.

### 3-5. 길안내 화면 — 다음 회전 예고 리스트 없음
- 프로토타입(10번)은 "다음 안내" 큐(예: "좌회전 준비 약 60m", "좌회전 약 20m")를 리스트로 보여준다.
- 현재 `NavigationScreen.kt`는 현재 action 1개 + `nextTurnType` 힌트 문구(예: "좌회전 예정") 정도만 표시, 회전 지점까지의 목록형 프리뷰는 없다.
- **판단**: `RouteStep` 데이터는 이미 서버에서 받고 있으므로(`FetchRouteUseCase`), 표시만 추가하면 되는 비교적 가벼운 작업.

### 3-6. 길안내 화면 — 지팡이 배터리/연결 상태 미표시
- 프로토타입(10번)은 "78% · 연결됨" 배터리·연결 상태를 안내 화면 하단에 상시 노출.
- 현재 `NavigationScreen.kt`에는 배터리/연결 상태 UI 자체가 없다. `DeviceResponse`/`Device` 도메인 모델에 배터리 필드가 있는지 확인 필요 — 없다면 백엔드 확장이 선행돼야 하는 항목.

### 3-7. 보호자 등록 — 전화번호 인증(OTP) 없음
- 프로토타입(06번)은 "인증번호 받기" 버튼으로 보호자 전화번호를 SMS 인증한 뒤에만 "등록하기"가 활성화되는 흐름.
- 현재 `GuardianScreen.kt`는 이름+전화번호 입력만으로 바로 등록 가능, 전화번호 검증 단계가 없다.
- **판단**: PRD에도 없는 기능이라 의도적 축소로 보이나, "허위 번호 등록 시 SOS가 전달되지 않는다"는 리스크가 있어 우선순위 논의가 필요.
