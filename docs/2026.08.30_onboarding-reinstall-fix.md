# 재설치 시 온보딩 재요구 버그 수정

## 문제 상황

앱을 삭제 후 재설치하면, 서버 계정에 이미 지팡이(기기)와 보호자 정보가 등록되어 있어도
로그인 직후 온보딩 화면(기기 등록 → 보호자 등록)으로 다시 진입한다.

## 원인

온보딩 완료 여부(`isFirst`)를 판단하는 유일한 기준이 **서버 데이터가 아니라 로컬 전용 값**이다.

- `AuthRepositoryImpl.login()` / `loginWithGoogle()`가 `tokenStorage.deviceId == null` 로 `isFirst`를 계산한다.
  (`data/repository/AuthRepositoryImpl.kt:36`, `:45`)
- `tokenStorage.deviceId`는 `EncryptedSharedPreferences`(`data/local/TokenStorage.kt`)에 저장되는 로컬 값이며,
  앱을 삭제하면 함께 사라진다.
- 이 값이 세팅되는 곳은 코드베이스 전체에서 `DeviceRepositoryImpl.registerDevice()` 성공 시 단 한 곳뿐이다
  (`data/repository/DeviceRepositoryImpl.kt:19`). 즉 "이 기기(앱 인스턴스)에서 등록을 완료한 적이 있는가"만 알 수 있고,
  "서버 계정에 이미 등록되어 있는가"는 전혀 확인하지 않는다.
- `NavGraph.kt:75`는 이 `isFirst` 값을 그대로 받아 `true`면 `Screen.Device.route`(온보딩)로 강제 이동시킨다.

반면 서버 조회 API(`DeviceApi.getDevices()` → `GET api/v1/devices`)는 이미 구현되어 있지만
로그인 흐름 어디에서도 호출되지 않는다 (`MypageViewModel`에서만 사용 중).

## 수정 방안

로그인 성공 직후 `DeviceApi.getDevices()`를 호출해 서버에 이미 등록된 기기가 있는지 확인하고,
있으면 그 기기 정보로 로컬 `tokenStorage.deviceId`를 복원한 뒤 `isFirst = false`를 반환한다.
(보호자 등록 여부는 기존에도 온보딩 완료 판정에 쓰이지 않았으므로 — 온보딩 중 "건너뛰기"로도
바로 `DestinationList`로 넘어감 — 그대로 둔다.)

네트워크 오류 등으로 서버 조회 자체가 실패하는 경우, 기존 동작(로컬 `deviceId` 유무)으로 폴백해
로그인 자체가 실패 처리되지 않도록 한다.

### 데이터 흐름

```
로그인 성공(토큰 저장)
  → DeviceRepository.getDevices() 호출 (GET api/v1/devices)
      성공 & 목록 비어있지 않음 → tokenStorage.deviceId = devices[0].deviceId, isFirst = false
      성공 & 목록 비어있음      → isFirst = true
      실패(네트워크 오류 등)    → isFirst = (tokenStorage.deviceId == null)  // 기존 동작 폴백
  → LoginEvent.NavigateAfterLogin(isFirst)
  → NavGraph: isFirst ? Screen.Device : Screen.DestinationList
```

### 수정 파일

```
domain/repository/AuthRepository.kt        (수정 없음 — 시그니처 변경 없음)
data/repository/AuthRepositoryImpl.kt      (수정) DeviceRepository 주입, isFirst 산출 로직 교체
```

`AuthRepositoryImpl`:

```kotlin
@Singleton
class AuthRepositoryImpl @Inject constructor(
    private val authApi: AuthApi,
    private val tokenStorage: TokenStorage,
    private val deviceRepository: DeviceRepository,   // 추가
) : AuthRepository {

    override suspend fun login(email: String, password: String): Result<Boolean> =
        runCatching {
            val response = authApi.login(LoginRequest(email, password))
            tokenStorage.accessToken  = response.accessToken
            tokenStorage.refreshToken = response.refreshToken
            tokenStorage.userId       = response.userId
            tokenStorage.userEmail    = email
            resolveIsFirst()
        }

    override suspend fun loginWithGoogle(idToken: String): Result<Boolean> =
        runCatching {
            val response = authApi.loginWithGoogle(GoogleLoginRequest(idToken))
            tokenStorage.accessToken  = response.accessToken
            tokenStorage.refreshToken = response.refreshToken
            tokenStorage.userId       = response.userId
            resolveIsFirst()
        }

    private suspend fun resolveIsFirst(): Boolean =
        deviceRepository.getDevices().fold(
            onSuccess = { devices ->
                val existing = devices.firstOrNull()
                if (existing != null) {
                    tokenStorage.deviceId = existing.deviceId
                    false
                } else {
                    true
                }
            },
            onFailure = { tokenStorage.deviceId == null },
        )

    // signup / verifyEmail / logout / getUserInfo 변경 없음
}
```

- API 요청/응답 포맷 변경 없음 (기존 `GET api/v1/devices` 재사용).
- DB 스키마 변경 없음.
- `AuthRepository` 인터페이스 시그니처 변경 없음 — `AuthRepositoryImpl` 내부 구현만 변경.
- 순환 의존 없음: `DeviceRepository`는 `TokenStorage`/`DeviceApi`에만 의존하고 `AuthRepository`를 참조하지 않음.

## 테스트 방법

1. 계정 A로 로그인 → 기기/보호자 등록 → 앱 삭제 → 재설치 → 같은 계정으로 로그인
   → 온보딩 없이 바로 목적지 리스트 화면으로 진입하는지 확인.
2. 기기 등록을 한 번도 하지 않은 신규 계정으로 로그인 → 정상적으로 온보딩(기기 등록) 화면으로 진입하는지 확인(회귀 방지).
3. 네트워크를 끈 상태에서 로그인 → 로그인 자체는 실패하지 않고, 로컬 `deviceId` 유무에 따라 기존과 동일하게 분기하는지 확인.
4. (선택) `AuthRepositoryImplTest` 유닛테스트: `getDevices()`가 비어있지 않은 리스트 반환 시 `login()` 결과가 `false`인지, 빈 리스트/실패 시 각각 기대값대로인지 검증.
